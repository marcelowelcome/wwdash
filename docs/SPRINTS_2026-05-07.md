## Sprint 1 — Críticos de segurança (07/mai manhã, ~75 min) 🔴

**Goal:** Eliminar exposições óbvias antes de qualquer outro trabalho. Todos os itens têm fix bem definido e baixo risco.

### 1.1 Auth + rate-limit em `/api/chat` (30 min)
- **Problema:** [app/api/chat/route.ts](../app/api/chat/route.ts) sem auth — qualquer um com a URL queima `OPENAI_API_KEY`.
- **Fix:** Adicionar `Authorization: Bearer ${CHAT_API_KEY}` com `timingSafeEqual` (espelho do padrão usado em [lib/board/auth.ts](../lib/board/auth.ts)). Reusar `lib/board/rate-limit.ts` com bucket `chat:<ip>` (10 req/min).
- **Vars novas:** `CHAT_API_KEY` no `.env.local` + Vercel.
- **Aceite:** `curl /api/chat` sem header → 401. Com header válido + 11 chamadas em 60s → 429 na 11ª.
- **Validação:** rodar 5 cenários de smoke no Vercel após deploy.

### 1.2 Setar `SYNC_SECRET` (5 min)
- **Problema:** `.env.local:28` vazio. Fallback `origin.includes('localhost')` não barra subdomain attack.
- **Fix:** `openssl rand -hex 32`, salvar em `.env.local` E Vercel `weddings-kpi`. Re-deploy.
- **Aceite:** `/api/sync` POST sem header → 401.

### 1.3 Aplicar RLS migration (10 min)
- **Problema:** RLS = "allow all" há 3 semanas. Anyone com URL+anon key pode dump completo de `deals`.
- **Fix:** Aplicar [dash-webhook migration `20260416_tighten_rls.sql`](../../dash-webhook/supabase/migrations/20260416_tighten_rls.sql) via Supabase Dashboard → SQL Editor.
- **Aceite:** `curl ${URL}/rest/v1/deals?select=*` com anon key → 0 rows ou 403. Service-role-key continua funcionando (Edge Functions, /api/metrics).
- **⚠ Cuidado:** validar que Dashboard ainda carrega (anon key precisa de SELECT em `deals`, `monthly_targets`, `ads_spend_cache`, `field_meta`, `stages`, `sync_logs`). Smoke test imediato após apply.

### 1.4 Rotacionar `BOARD_API_KEY` (15 min)
- **Problema:** Chave em texto puro em `/home/marcelo/DashWW/.secrets-cowork.md` + vazada em chats anteriores.
- **Fix:**
  1. `openssl rand -hex 32` → nova chave
  2. Vercel `weddings-kpi` → atualizar env var → re-deploy
  3. Cowork → atualizar config interno
  4. Atualizar `.secrets-cowork.md`
  5. **Smoke test board endpoint** com chave antiga (deve dar 401) e nova (deve dar 200)
- **Aceite:** `curl /api/board/weekly` com chave antiga → 401, com nova → 200.

### 1.5 Cleanup WIP raiz (10 min — pode rodar paralelo)
- **Problema:** `sdr_dash_v2.jsx`, `sdr_investigation_dash.jsx`, `sdr_investigation_dash (1).jsx`, `check_*.mjs` × 5, `dump_raw.mjs` em `kpi-weddings/` raiz.

## Sprint 2 — Métricas de receita (Closer v2.9.x) (07/mai tarde, 3-4h) 🟠

**Goal:** Completar o redesign Closer com as métricas growth de **monetização** que ficaram fora do v2.9.0. Sem essas métricas, dashboard não responde "estamos crescendo de forma rentável?".

> **Estado atual (v2.9.0 já em prod):**
> - ✅ Funil 3 etapas (Agendada → Realizada → Fechado)
> - ✅ CAC, CPL, Tempo até Fechamento
> - ✅ Conv MQL → Contrato (linha derivada)
> - ✅ Cohort de Fechamento (% fechou / aberto / perdeu)
> - ✅ Top motivos de perda (preservado da v1)
>
> **Faltando para responder "growth saudável?":**

### 2.1 Ticket médio (45 min)
- **Métrica:** `avg(valor_fechado_em_contrato)` para deals com `data_fechamento` no período.
- **Onde:** [lib/metrics-closer.ts](../lib/metrics-closer.ts) — adicionar `RevenueBlock { ticketMedio, ticketP50, ticketP90, contratos, receitaTotal }`.
- **UI:** card no bloco econômico, ao lado de CAC. Tooltip explicando "valor médio do contrato fechado no período".
- **Edge cases:** filtrar valores `<= 0` (zerados ou inválidos), `null`, e outliers acima de R$ 500k (típico WW = R$ 30-80k).
- **Aceite:** novo teste em metrics-closer.test.ts validando avg, edge cases. Validar contra Supabase.

### 2.2 ROAS (30 min)
- **Métrica:** `(ticketMedio × contratos) / spend` no período.
- **UI:** big number destacado no bloco econômico. Cor verde se >= 3, âmbar 1.5-3, vermelho < 1.5 (defaults — ajustar com user).
- **Tooltip:** "Receita gerada para cada R$ 1 investido em ads. Não considera ticket de upsell ou cross-sell."
- **Aceite:** teste unitário (zero spend → null; zero contratos → 0).

### 2.3 LTV:CAC ratio (20 min)
- **Métrica:** `ticketMedio / CAC`. Proxy de saúde unit economics.
- **UI:** badge ao lado do CAC. "LTV:CAC 4.2× ✓"
- **Defaults:** verde >= 3, âmbar 1-3, vermelho < 1.
- **Caveat:** documentar no tooltip que ticket atual ≠ LTV real (não considera repeat / lifetime). É um lower-bound.
- **Aceite:** teste unitário com CAC=0 (retorna null), com ticket=0 (retorna 0).

### 2.4 Win rate por destino (1h)
- **Métrica:** Para cada `destino` no período, `contratos / leads`. Tabela top-10 destinos por volume.
- **UI:** card abaixo do funil ou aba secundária. Cada linha tem `destino`, `leads`, `contratos`, `%`. Click → DealsModal filtrado por destino + ganhos.
- **Insight de growth:** identifica onde investir mais ads (destinos high-conv) vs onde otimizar funil (destinos high-volume + low-conv).
- **Aceite:** teste unitário com fixtures multi-destino.

### 2.5 Decisões de produto a confirmar com usuário ANTES de implementar
1. **Outlier guard** para ticket médio: limite superior R$ 500k? Ou escala log?
2. **ROAS thresholds:** verde >=3 ou >=4 para WW (alta margem)?
3. **LTV proxy:** usar só `valor_fechado_em_contrato` ou somar `wt_enviado_pagamento_de_taxa` + futuros upsells? (Provavelmente V1 = só contrato.)
4. **Win rate por destino:** considerar apenas leads com `destino IS NOT NULL`? Ou agrupar `null` como "Sem destino definido"?

### 2.6 Aceite Sprint 2
- 4 cards novos no bloco econômico do Closer (Ticket Médio, ROAS, LTV:CAC) + 1 card de Win rate por destino
- ≥6 testes novos em `metrics-closer.test.ts`
- Validação contra Supabase em ≥1 mês (cross-check manual)
- Tooltip preciso em cada card
- Bump versão `2.9.0 → 2.9.1`

**Estimativa:** 3-4h focado.
